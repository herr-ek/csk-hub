## WEB-001 — Normalize return destinations before accepting them as internal

- Type: security risk. Severity: **Medium**. Confidence: **Confirmed**. Owner: `src/core/navigation/navigation-utils.ts`. Effort: **S**. Dependencies: none.
- Evidence: `src/core/navigation/navigation-utils.ts:4-9,13-20`; `src/features/account/login/login-form.tsx:25-38`; `src/features/account/two-factor/use-two-factor-form.ts:11-14,44`. Validator checks the raw prefix and backslashes. Decoded `returnTo` then reaches `router.replace`.
- Observed: `/\t/example.com`, `/\n/example.com`, and `/\r/example.com` pass the current predicate. A read-only Node WHATWG URL probe resolves each to `https://example.com/` against `https://hub.example`. The installed Next router uses `new URL(addBasePath(href), location.href)` in `node_modules/next/dist/client/components/app-router-instance.js:219` and sets `isExternalUrl` at line 228. This is a confirmed origin-boundary mismatch, not a claim of session/token exfiltration.
- Impact: an attacker-controlled login link such as `?returnTo=%2F%09%2Fexample.com` can take a member to an external site immediately after successful authentication, lending credibility to phishing. The value also survives the two-factor hop.
- Recommendation: one application-owned parser should reject control characters, protocol-relative paths and backslashes; resolve against a trusted fixed application origin and require equal origin, then return canonical pathname/search/hash. Have all helpers consume the parsed safe destination rather than separately checking and preserving the unsafe raw input.
- Tradeoff: strict control-character rejection is a small local fix; a parsed/canonical return type makes future callers harder to misuse. Preserve valid query strings and hashes. Avoid a broad URL allowlist for this internal-only contract.
- Acceptance/verification: table-driven checks cover tab/newline/carriage-return variants, protocol-relative URLs, backslashes, external schemes, valid internal path/query/hash and the encoded `returnTo` → decoded query → 2FA → login flow. No accepted destination resolves to another origin. Verify a local successful-login flow with a fake destination only in a disposable environment.

## WEB-002 — Subscribe password forms to submission state

- Type: bug. Severity: **Medium**. Confidence: **Confirmed**. Owner: account password workflows. Effort: **S**. Dependencies: none; coordinate with [AUTH-005](authentication.md#auth-005).
- Evidence: `src/features/account/password-reset/password-reset-request-form.tsx:50-57,87-94`; `src/features/account/password-reset/password-reset-form.tsx:53-60,139-140`; `src/features/account/settings/security/password/password-settings.tsx:59-65,97-98`. All read `form.state.isSubmitting` directly during render without subscribing. Correct local precedent: `src/features/account/login/login-form.tsx:72` uses `useSelector`.
- Observed: installed TanStack `useForm` returns a stable object whose `state` property reads `formApi.store.state`, without subscribing the parent (`node_modules/@tanstack/react-form/src/useForm.tsx:206-276`). Therefore successful initial renders with null error/message do not re-render when submission starts; the disabled state, busy announcement and pending label stay stale. Child `form.Field` subscriptions do not subscribe siblings/parent. [Official reactivity guidance](https://tanstack.com/form/latest/docs/framework/react/guides/reactivity) requires `useSelector` or `form.Subscribe`.
- Additional verification: a disposable Node script constructed the installed `FormApi`, held `onSubmit` on one deferred promise, and called `handleSubmit` twice. Output was `{"callsBeforeResolve":2,"isSubmitting":true,"canSubmit":false}`. Its internal submission handling does not reliably substitute for disabled UI/explicit in-flight guarding on the repeated submission path (`node_modules/@tanstack/form-core/src/FormApi.ts:2420-2465`). No real auth requests were sent.
- Impact: members receive no pending feedback and can repeat reset-email or password-changing requests during slow responses, introducing confusing racing outcomes and email duplication.
- Recommendation: subscribe narrowly to `isSubmitting`, use it consistently for button and `aria-busy`, and guard repeated entry at the submission boundary where duplicate side effects matter. Reuse the existing login pattern; do not introduce a generic form framework.
- Tradeoff: `form.Subscribe` limits render scope; `useSelector` is simpler when parent `aria-busy` also depends on pending state.
- Acceptance/verification: defer mocked request completion in a meaningful UI test; pending label, disabled submit and busy state appear on the first request and reset after success/failure; repeated clicks/Enter do not launch additional requests. Cover one workflow with the shared pattern plus proportionate checks for the other two.

## WEB-003 — Recover from rejected account operations and reconcile uncertain changes

- Type: bug. Severity: **Medium**. Confidence: **Confirmed** for rejection paths; real browser outage not exercised. Owner: account client operation/result boundaries and workflow hooks. Effort: **M**. Dependencies: coordinate stable error kinds with I18N-001 and reset protocol work.
- Evidence: `src/features/account/two-factor/use-two-factor-form.ts:23-38`; `src/features/account/two-factor/service.ts:11-35`; `src/features/account/settings/security/two-factor/use-two-factor-settings.ts:19-56`; `src/features/account/settings/security/two-factor/two-factor-service.ts:9-34`. Hooks set pending before `await` and clear it only afterward; adapters do not catch rejected transport requests. The configured auth client (`src/core/auth/auth-client.ts:15-25`) does not enable catch-all fetch handling. Installed Better Fetch only normalizes transport exceptions when `catchAllError` is explicitly enabled (`node_modules/@better-fetch/fetch/dist/index.js:499-522`); raw fetch rejection propagates otherwise (line 628).
- Related occurrences: `src/features/account/settings/security/password/password-settings.ts:21-37` neither catches rejected `changePassword` nor renders a transport failure; `src/core/navigation/logout-button.tsx:15-22` restores pending with `finally` but ignores returned errors and has no catch/visible failure; initial passkey loading in `src/features/account/settings/security/passkeys/passkey-settings.tsx:35-44` drops a rejected promise and initially represents unknown state as no passkeys. Good examples already exist in `settings/profile/email-verification.tsx:30-76` and passkey mutations (try/catch/finally).
- Impact: an offline/interrupted 2FA request leaves the workflow disabled indefinitely until reload, particularly painful while signing in or changing authentication settings. A response lost after a server commit also leaves client state uncertain.
- Recommendation: make operation boundaries return stable transport/unavailable outcomes; clear pending in `finally` in every hook that owns pending state. Present localized retry guidance. For authentication-setting writes, reload authoritative setting/session state after an ambiguous response instead of asserting that nothing changed; do not automatically replay secret-changing operations. Add visible sign-out/stop-impersonating failure and separate loading/error/empty states for the passkey list while visiting the same boundary.
- Tradeoff: a small helper is appropriate only if it hides a stable repeated protocol; workflow-specific reconciliation must remain with the owning feature. A global catch-all alone will not supply correct recovery or localized wording.
- Acceptance/verification: mock/reject each adapter request and ensure controls recover and an accessible localized error appears. Check the response-lost-after-success case for 2FA state reconciliation. Verify sign-out failure is visible and does not imply success; passkey list fetch failure never displays only an empty state. No production account changes required.

## WEB-004 — Provide application-owned denied, missing and failed route states

- Type: readiness gap. Severity: **Medium**. Confidence: **Confirmed** source inventory. Owner: `src/app` route error presentation plus proxy/access-decision adapter. Effort: **M**. Dependencies: access-control outcome design; localized messages from I18N-001.
- Evidence: no `error.tsx`, `global-error.tsx` or `not-found.tsx` exists beneath `src/app`. `src/proxy.ts:33-35` returns an empty 403. `src/core/auth/route-access.ts` deliberately denies impersonated messaging. `src/core/navigation/app-navigation.tsx:25-34` still includes Messages for every authenticated navigation configuration. `src/features/posts/post-screen.tsx:31-34` and `src/app/[locale]/(app)/messages/[conversationId]/page.tsx:37` call `notFound`, relying on framework fallback. Proxy session/preferences work at `src/proxy.ts:14-16` runs before route rendering, so an RSC error boundary alone cannot catch those failures.
- Observed: an impersonating Admin has a visible Messages link whose denial response is an empty body. Unexpected page/read failures and missing records have no application-owned localized recovery state. This does not mean enforcement is absent.
- Impact: members get blank/technical fallback screens without useful navigation or recovery; an Admin can lose the convenient stop-impersonating navigation on a denied request.
- Recommendation: define localized unavailable/not-found/forbidden presentation consistent with chosen policy outcomes, preserve a safe return path and a way to stop impersonation, and add narrowly placed error boundaries with retry/navigation for render failures. Handle proxy failures at that boundary and retain operational diagnostics; do not turn database outages into forbidden decisions. Hide or explain unavailable navigation as an affordance while retaining server enforcement.
- Tradeoff: a simple forbidden route/response may fit better than adopting another framework feature. Choose a solution that preserves intended HTTP status and locale semantics without importing request-bound translation configuration where root params are unavailable. No elaborate error-page framework needed.
- Acceptance/verification: in a disposable app, exercise unauthorized admin path, messaging while impersonating, missing Post/Conversation and a mocked read failure; each shows appropriate localized content and recovery, no raw exception detail, and expected status. Verify proxy-level database failure separately from component failure. [Next error handling guidance](https://nextjs.org/docs/app/getting-started/error-handling); installed `node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md` is authoritative for this version.

## WEB-005 — Distinguish failed member searches from no matching members

- Type: bug. Severity: **Low**. Confidence: **Confirmed** for failure-to-empty mapping. Owner: messaging new-Conversation member picker. Effort: **S**. Dependencies: localized error copy.
- Evidence: `src/features/messaging/ui/inbox/member-combobox.tsx:35-42,68-75` catches every failed search and sets members to `[]`; the render shows the no-members message whenever not loading. No failure state or retry affordance exists.
- Impact: a network/server error falsely tells the member their intended Conversation partner cannot be found. Debouncing and latest-request protection are otherwise useful and should remain.
- Recommendation: model pending, result/empty and failed search separately, render a localized recoverable error, and retain latest-request protection for successes and failures. Retrying the unchanged query must be possible.
- Additional pending-state concern (Strongly probable; do not promote to confirmed without a UI probe): the `startTransition` callback does not return or await `searchMembersAction`. The [React API](https://react.dev/reference/react/useTransition) includes awaited async work in a transition; the installed React source checks the callback's returned thenable. However, Next Server Action dispatch itself uses transitions, so a browser test should settle whether the surrounding `loading` flag currently spans the request before changing it. Explicit request state is an uncomplicated alternative.
- Acceptance/verification: reject the search promise, resolve zero results, resolve positive results, and resolve an older query after a newer one. Each must show the correct distinct state; retry succeeds; stale completions never replace newer results. Assert loading with a delayed promise if retaining transition-based state.

## I18N-001 — Bring validation, failure and primitive copy into the locale contract

- Type: bug/convention issue. Severity: **Medium**. Confidence: **Confirmed**. Owner: account presentation/error contracts and shared UI label props, coordinated by core i18n. Effort: **M**. Dependencies: WEB-003 and auth workflow error/result changes should use the same stable error kinds.
- Evidence: `src/shared/schemas.ts:4-14` produces English strings; `src/features/account/login/schemas.ts:4-6`, `src/features/account/password-reset/schemas.ts:4-16`, and security/password schemas pass English labels/messages; `src/features/account/login/login-form.tsx:100,123` and reset form FieldErrors display these directly. `src/features/account/login/service.ts:33-34,61-65,96-100,126-130`, `src/features/account/password-reset/service.ts:7-8,43-55`, and two-factor services return English fallback copy. Shared visible/a11y copy also bypasses catalogs: `src/shared/ui/base/dialog.tsx:64` hardcodes Close and `src/shared/ui/base/toast.tsx:105` hardcodes Close toast; both are used by real workflows. Biome's JSX rule cannot inspect service string contracts and `biome.json:56-65` deliberately exempts shared primitives.
- Observed: switching the Hub to Swedish or German changes ordinary labels but validation/transport fallbacks remain English; built-in dialog close labels do too. This is a completeness defect, not criticism of any translated wording.
- Recommendation: return stable validation/error codes and parameters from universal/service modules and translate at the presentation edge. Preserve shared → core dependency direction: let reusable primitives receive translated close-label props/context supplied by the app rather than import core i18n. Inventory used controls only, not every unused generated primitive. Include date formatting while touching relevant account presentation: sessions use `Intl.DateTimeFormat(undefined)` (`settings/security/sessions/sessions-settings.tsx:13`) and passkeys call `toLocaleDateString()` (`passkey-settings.tsx:152`), ignoring the explicitly selected app locale; prefer the existing formatter façade.
- Completeness guard: `messages.test.ts:21-29` currently checks flattened keys only. A read-only ICU-parser check found all three catalogs have **382 leaves**, no missing/extra keys, no parse failures and matching argument/type sets. Retain that healthy baseline and extend the existing inexpensive catalog guard to parse ICU and compare required argument/type contracts when making this change; do not add translation wording tests. Locale-specific plural categories should remain legal.
- Tradeoff: a localized schema factory can be a small UI-side solution, but shared domain validation should not receive React hooks or reach into catalogs; code/parameter results provide a more reusable server/client boundary.
- Acceptance/verification: in all three locales trigger required/invalid-email/password-mismatch and offline fallback states in login/reset/settings; user-visible errors and dialog/toast accessible labels come from that locale. Locale switching affects account date formatting. Catalog parity and ICU checks pass, and a deliberately mismatched placeholder is rejected by the guard.
