## AUTHZ-001 — Put Admin target rules behind every entry point and preserve the final Admin atomically

- **Type / priority / confidence:** security risk and data-integrity risk / **High** / **Confirmed** HTTP policy bypass; **Strongly probable** concurrent loss of the final active Admin.
- **Locations:** `src/features/user-management/actions.ts:45–55,87–103,156–170`; `src/core/auth/permissions.ts:46–50`; `src/app/api/auth/[...all]/route.ts:4`; installed `better-auth/dist/plugins/admin/routes.mjs:43–80,240–298,506–539`.
- **Observed:** app actions prohibit self role changes and check the final active Admin before demotion/deactivation. The public native `/admin/set-role` endpoint checks global permission and target existence, then updates the role without those rules. `/admin/update-user` is another role/state write surface. The current grants inherit the library's broad Admin powers. App last-Admin checks count rows separately from the later write; there is no shared transaction or serialization mechanism.
- **Impact/inference:** the sole Admin can demote themselves through the native endpoint despite the app's prohibition. Two Admins can pass separate checks and concurrently demote/deactivate each other, leaving no active Admin. These are authenticated Admin operations, not a demonstrated ordinary-User privilege escalation. The native plugin correctly rejects self-ban and reads authoritative sessions; retain those protections. Erasure endpoints were deliberately not analyzed.
- **Change / owner:** user-management should own one command boundary for role and activity changes, using descriptive target policies. Restrict duplicate native HTTP write paths or make them run exactly the same policy. Use an explicit set of required plugin grants instead of spreading all defaults. Serialize the count-and-change invariant across every relevant writer, with actor/target state revalidated inside that operation. Do not hold a transaction open around an unrelated Better Auth connection and assume its write participates; choose a supported transactional adapter/hook or an application-owned transaction that also preserves required session revocation.
- **Tradeoff / dependencies / effort:** retain Better Auth for identity and native mechanisms; target policy belongs to the app. A narrowly scoped transactional lock is sufficient at this scale. Depends on the authoritative actor in AUTH-004; can close direct HTTP bypass first. **M–L**.
- **Acceptance:** every HTTP/action/server API path observes self/target/final-Admin rules; unknown role input cannot grant authority; simultaneous lifecycle changes leave at least one active Admin; native session revocation remains effective. Stored `admin` and `user,admin` representations retain equivalent product meaning.
- **Verification:** direct native-handler tests for self-demotion and alternative update paths, normal User denial, and a disposable PostgreSQL concurrent two-Admin scenario. App-action unit tests alone do not cover the native surface. [Better Auth Admin API](https://better-auth.com/docs/plugins/admin) documents the separate native routes.

## AUTHZ-002 — Preserve impersonation identity through private workflows and credential changes

- **Type / priority / confidence:** security risk / **High** / **Confirmed** missing enforcement and enrollment challenge; **Strongly probable** persistent target-account access via completed enrollment.
- **Locations:** `src/core/auth/session.server.ts:19–24`; `src/core/auth/permissions.server.ts:25,101–110`; `src/core/auth/route-access.ts:55,79–81`; `src/features/messaging/sending/send-message.ts:14`, `start-direct-conversation.ts:17`; `src/features/messaging/ui/conversation/read.ts:13`; `src/features/account/settings/account-settings.tsx:25–30`; `src/core/auth/permissions.ts:46–50`.
- **Observed:** only the route policy rejects impersonated messaging. Messaging commands/read helpers obtain an ID from `requireAuthenticatedUser`, which discards `impersonatedBy`; none enforce the same prohibition. Account security controls remain available. Installed passkey registration uses fresh-session middleware that checks age, not impersonation (`@better-auth/passkey/dist/index.mjs:88,324`; `better-auth/dist/api/routes/session.mjs:324–340`). A synthetic impersonated session received a registration challenge, HTTP 200. Full WebAuthn enrollment was not performed. Default native Admin grants also include `set-password`, `set-email`, and `update`.
- **Impact/inference:** route-only restrictions do not establish a command policy. A known Server Action can be submitted through an allowed app route; the callable command currently accepts the target identity. More seriously, fresh impersonation can potentially enroll an Admin-owned passkey, allowing later target login without the impersonation marker. Broad native credential powers can defeat the same privacy intent independently. Do not claim messaging is private from all Admin credential powers today.
- **Change / owner:** core auth should return an authoritative actor retaining real actor, effective User, session, and impersonation state. Messaging must reject impersonated actors at reads, search, send, and read-cursor commands. Core auth must enforce the selected credential policy on native passkey, password, email, 2FA, and recovery/session mutation paths, with UI affordances reflecting it. Deny credential enrollment/rebinding during impersonation by default; explicitly review native Admin password/email powers. Allow ending impersonation even when the target workflow is forbidden.
- **Tradeoff / dependencies / effort:** product must ratify whether acting as a User is a support capability or includes credential takeover. Recommendation: support capability; private Conversations and security credentials remain excluded. This follows the existing messaging route restriction. Depends on AUTH-004 and native-path work in AUTHZ-001/AUTH-003. **M**. No durable audit system is required.
- **Acceptance:** direct private command calls and native enrollment/mutation calls reject impersonated actors; changing URL does not evade policy; normal self-service works; stop-impersonating works from denied/error states; an Admin cannot gain an unmarked target identity via a supposedly restricted support workflow.
- **Verification:** actor-policy matrix; direct action/service calls with impersonation set; native-handler registration-options and credential mutation tests; one disposable browser WebAuthn ceremony if supported. Verify both HTTP and server API paths. [Next data-security guidance](https://nextjs.org/docs/app/guides/data-security) explains why action and data authorization must be independent of page visibility.

## ARCH-001 — Make sensitive read and server-only contracts local to their owning modules

- **Type / priority / confidence:** architecture risk / **Medium** / **Confirmed** missing guards/contracts; no current client-secret leak demonstrated.
- **Locations:** `src/core/db/index.ts:1`, `src/core/config/env.ts:1`, `src/core/auth/auth.ts:1`, `src/core/auth/permissions.server.ts:1`; `src/features/user-management/invite-user.ts:1`; `src/features/user-management/service.ts:7`; `src/features/posts/service.ts:22,41`; `docs/codebase-structure.md:129–133`.
- **Observed:** the secret/config, DB and auth leaves omit the documented `server-only` boundary. Naming a file `.server.ts` is not a Next build guard. `listUsers` and Post reads expose records without establishing identity/policy inside their read contract; current callers rely on page/proxy checks. Messaging reads already demonstrate a stronger local authentication contract. User-management and Post actions contain persistence logic directly despite the documented command-boundary preference.
- **Impact:** future agents must remember which callers authorize which reads and which imports are safe. Adding one legitimate route or client import can bypass an implicit assumption. This is a change-locality defect rather than evidence of a presently reachable unauthenticated Post disclosure.
- **Change / owner:** add leaf guards to actual server capabilities; keep schemas/types/pure policies universal. Put authenticated/policy-aware, deliberately shaped reads at feature entry boundaries. Internal raw queries may accept an already authorized actor and remain private; do not require every low-level helper to repeat database session lookup. Extract a user-management command module while fixing AUTHZ-001; avoid unrelated mechanical file splits. Keep action adapters responsible for parsing, protocol results and invalidation.
- **Tradeoff / dependencies / effort:** guards affect CLI/seed/test imports; provide the appropriate server condition or a deliberate tool bootstrap rather than silently weakening app guards. Coordinate authoritative actor and policy adoption. **M**.
- **Acceptance / verification:** importing a protected leaf from a disposable Client Component fails at build time; normal universal schemas remain usable; exposed sensitive reads deny unauthenticated/forbidden callers; tools still initialize without client-module import tricks; architecture direction remains `app → features → core/shared` with no reverse edge. Verify a production build and focused read-contract tests. Do not add pass-through repositories or a universal query object.

## OPS-001 — Stop overriding PostgreSQL certificate verification

- **Type / priority / confidence:** security risk / **High** / **Confirmed**.
- **Locations:** `src/core/db/index.ts:4–9`; `.env.example:6–7`; installed `pg-connection-string/index.js:172–176`.
- **Observed:** any supplied `sslmode`, including `verify-full`, is rewritten to `no-verify`. A synthetic connection-string probe through installed `pg-connection-string` yields `ssl.rejectUnauthorized: false`. The example also suggests globally setting `NODE_TLS_REJECT_UNAUTHORIZED=0` for a production connection.
- **Impact:** encrypted database traffic loses server-certificate authentication, exposing database credentials/content to an attacker able to intercept or redirect that connection. No interception was attempted; this is a confirmed client configuration defect.
- **Change / owner:** core DB must honor the explicit deployment SSL contract, with verified TLS and the provider CA where needed. Remove the unconditional downgrade and global TLS-disable guidance. Keep local non-TLS PostgreSQL configuration explicit and separate.
- **Tradeoff / dependencies / effort:** may reveal a previously masked provider CA/configuration problem; fix trust configuration instead of disabling verification. No schema change. **S**.
- **Acceptance / verification:** verified production configuration remains verified after parsing; a wrong/untrusted certificate is rejected; a trusted provider certificate works; local Docker connection still works using its own configuration. Use disposable certificate/connection tests or deployment staging, never real credential capture. [node-postgres SSL documentation](https://node-postgres.com/features/ssl) explains connection-string and SSL-option interaction.

## OPS-002 — Make environment validation describe a usable and safe deployment

- **Type / priority / confidence:** bug and readiness gap / **High** / **Confirmed**.
- **Locations:** `src/core/config/env.ts:3,7–27,50–57`; `src/core/auth/auth.ts:64,77`; `src/core/email/client.ts:23–34`; `.env.example`; `README.md:42–52`; `scripts/seed-admin.ts:6–21`, `scripts/seed-users.ts:6–27`.
- **Observed:** the parsed environment prefers `ENVIRONMENT`, but `isProduction` tests only `VERCEL_ENV`. A synthetic `ENVIRONMENT=production` import prints `isProduction:false` and defaults email mode to `log`. Logging email returns success and writes the full message, including auth links/codes. Production does not reject this mode. Separately, following the sample after supplying an auth secret exits validation on empty SMTP_USER/PASSWORD/FROM and CONTACT_EMAIL, even with email log mode. Empty VAPID strings pass the schema. Development seed scripts have fixed passwords and no environment refusal; no evidence they ran against production was found.
- **Impact:** non-Vercel production skips intended email-verification policy and silently logs authentication messages rather than delivering them. Preview deployments with real accounts also need an explicit delivery policy. New contributors cannot follow the documented minimal setup successfully. Including `testUtils` outside Vercel production is unnecessary, but installed 1.7.4 exposes no public test endpoints; no test-endpoint exploit is alleged.
- **Change / owner:** core config should normalize one deployment environment with documented precedence and derive production decisions from it; do not equate every `NODE_ENV=production` build with a production deployment. Normalize optional blanks, validate URL/secret/key shape early without printing values, and express notification-enabled prerequisites explicitly. Require real delivery configuration for real production, keeping secret-bearing email logs a deliberate local mode. Align the example and README with that contract; guard development-only seed commands before writes.
- **Tradeoff / dependencies / effort:** decide whether push is optional locally or requires generated keys in setup; either is valid if explicit. Production origin changes coordinate with AUTH-002. SMTP `requireTLS` already exists and should remain. **M**.
- **Acceptance / verification:** table of development/test/preview/production and explicit/Vercel environment combinations resolves predictably; documented setup boots after the stated inputs; production rejects missing secret, invalid base origin, accidental log delivery and incomplete enabled push; diagnostics contain names/reasons, never secrets; seed commands refuse production before DB writes. Use isolated process/env tests and mocked email output; no production messages required.

## OPS-003 — Preserve operational failure signals without turning outages into access denial

- **Type / priority / confidence:** bug and readiness gap / **Medium** / **Confirmed**.
- **Locations:** `src/features/messaging/ui/message-command-result.ts:8–18`; `src/features/messaging/ui/inbox/actions.ts:25–26`; `src/features/messaging/ui/conversation/actions.ts:25–26`; `src/features/messaging/sending/README.md:115–117`; `src/core/auth/route-access.ts:85–90`.
- **Observed:** unexpected message-command exceptions become the user-safe `unexpected` result without logging the original failure category. The module README promises server observability. Route policy catches every permission-check exception and returns forbidden, including database/service errors. Post publish already distinguishes authorization denial from authorization lookup failure (`posts/actions.ts:39–50`).
- **Impact:** real database failures resemble permissions problems, and failed message writes provide no useful server diagnostic at their catch boundary. This makes support and reconciliation difficult even for a small association.
- **Change / owner:** preserve expected domain/auth outcomes as typed results; unexpected exceptions should emit a sanitized operational event once at the transport boundary and produce an unavailable result. Include operation, safe error code/name and a correlation identifier when available; avoid message text, auth tokens, push endpoint keys, or whole request bodies. Route adapters must distinguish denial from unavailable infrastructure. Apply the same principle to notification outcomes in NOTIFY-04.
- **Tradeoff / dependencies / effort:** use the existing best-effort logger; no persistent audit trail, logging platform or blanket telemetry project. Coordinate WEB-004 result presentation. **S–M**.
- **Acceptance / verification:** inject a DB failure and a genuine denial separately; they produce different result/status categories, safe UI, and the expected single diagnostic. Secret-bearing values never appear in the captured log. Successful/expected validation paths remain quiet.

## TOOL-001 — Declare the runtime packages actually used and align auth schema tooling

- **Type / priority / confidence:** readiness gap / **Medium** / **Confirmed** manifest mismatch; **Strongly probable** production-only install fragility, not a reproduced deployment outage.
- **Locations:** `package.json:26,33,49`; `src/core/db/index.ts:1`; `src/features/account/login/login-form.tsx:3`; `src/features/messaging/ui/message-timestamp.ts:1`; installed `@better-auth/cli/package.json` and `drizzle-orm/package.json`.
- **Observed:** the app uses Drizzle's node-postgres adapter but does not declare `pg` as a runtime dependency; it is installed through development CLI dependencies, while Drizzle and Better Auth mark it optional. App forms import `@tanstack/react-form` via the otherwise unreferenced `@tanstack/react-form-nextjs` wrapper dependency. A type imports `use-intl/core` transitively. `date-fns` has no source/config reference in the inspected tree. The schema command runs CLI 1.4.21, which embeds Better Auth 1.4.21 and Drizzle 0.41, against app auth 1.7.4 / Drizzle 0.45.2.
- **Impact:** clean or production-only dependency installation can differ from a developer's hoisted tree. Schema generation is version-sensitive, and the documented command currently mixes substantial package versions. No migrations or generated schema output were changed or reviewed to claim specific schema corruption.
- **Change / owner:** package/tooling configuration should directly declare runtime driver/form dependencies, remove an unused wrapper only after replacing its required import, and keep type imports behind the existing i18n façade where practical. Verify the currently supported auth generator and align its configuration-loading/schema contract with installed auth plugins. Remove genuinely unused dependencies such as date-fns only after confirming all scripts. Do not delete unused reusable UI primitives solely from reachability results.
- **Tradeoff / dependencies / effort:** dependency cleanup itself is small; generator compatibility needs a disposable output comparison. Coordinate ARCH-001's CLI server-only bootstrap. **S–M**.
- **Acceptance / verification:** fresh production-only install resolves the runtime adapter and needed packages; full install/build works from the lockfile; auth generation into a temporary output reads the intended 1.7 schema without loading an older incompatible auth model; no source schema is overwritten until differences are reviewed. [Drizzle PostgreSQL setup](https://orm.drizzle.team/docs/get-started-postgresql) explicitly includes the selected driver; [Better Auth CLI](https://better-auth.com/docs/concepts/cli) is the current tooling reference.

## DOC-001 — Replace the stale entry map and keep behavioral contracts with their owners

- **Type / priority / confidence:** documentation issue / **Medium** / **Confirmed**.
- **Locations:** `README.md:11–13,86–100,102–111`; `docs/codebase-structure.md:82,129–133`; `AGENTS.md`; `src/core/i18n/README.md`; `src/features/messaging/README.md`; `src/features/messaging/sending/README.md:115–117`.

Setup has the mismatch in OPS-002. The structure guide refers to a generated Drizzle client although this app exports hand-maintained Drizzle table definitions and auth-generator output; blanket regeneration guidance obscures that ownership distinction. Module-local i18n/preferences/notifications/messaging docs already exist but are not a complete root navigation map. Operational-contract drift is OPS-003.
- **Impact:** a future agent starts with an incorrect product inventory and may create duplicate work, use the wrong edit/generation boundary or miss the workflow-specific invariants. The source itself is generally more current than the root README.

Keep vocabulary in CONTEXT, team decisions in ADRs, code placement in the structure guide, detailed contracts beside modules, and planned work in GitHub Issues. Clarify auth schema generation versus app-owned schema files. Update setup only after OPS-002's contract is decided. Add a contents list to the structure guide; split by stable ownership only when sections genuinely grow, rather than imposing an arbitrary line limit.
- **Tradeoff / dependencies / effort:** update existing canonical docs and link to them; do not duplicate policy bodies across AGENTS, README and feature docs. ADR drafts are permitted; the review is not team agreement and must not be presented as a merged ADR. Depends on the accepted environment/policy outcomes. **S**.
- **Acceptance / verification:** a new agent can find each current feature, workflow owner and check from README; route/status statements match this snapshot or subsequent changes; generator instructions name the actual owned files; local links resolve; no unmerged ADR is linked from external issues as an accepted remote-master decision. Existing review prompt/index remain preserved by this review pass.
